# 抖音连麦主播名单迁移

当前阶段：源码迁移和本地验证完成，待实际直播验证识别效果。

## 已确认的范围

- 在 fork 的 `custom` 分支中维护源码功能，后续由远程构建的镜像提供功能。
- 本次不迁移小红书补丁，保持上游实现；实际出现问题后再评估。
- 将原抖音补丁迁移为“连麦主播名单”功能。
- 记录其他连麦或 PK 主播的昵称、抖音号、UID、主页和首次发现时间。
- 排除当前录制主播本人、普通上麦观众。
- 按一次录制去重：从开始到停止录制为一次，视频分段和弹幕重连不重置名单；停止后重新录制或程序重启后重新开始录制，重新统计。
- 不承诺完整连麦次数、持续时间或准确上下麦时间。
- 新增独立的全局“记录连麦主播”开关，新配置默认关闭，不提供单个直播间覆盖。
- 修改开关从下一次录制生效，正在录制的任务保持启动时设置。
- 开启名单记录时，即使关闭弹幕保存，也建立消息连接以接收连麦消息，不保存普通弹幕和礼物。
- 保留上游 Cookie 模式。
- 名单解析或写入失败不影响录像；记录错误日志和录制时间线提示。
- 尚未成功写入的主播保留在内存中，后续消息或录像分段时重试，停止录制时再尝试一次；持续失败明确提示，不无限阻塞停止。

## 输出与识别规则

- 每次录制生成独立的 UTF-8 文本，放在首次录像文件所在目录，以其基础名称加 `.连麦记录.txt` 命名。
- 后续视频分段继续写入同一份名单，即使分段目录变化也不拆分。
- 每行保存主播首次发现时间、昵称、抖音号、UID 和主页。时间采用录制进程所在时区。
- 没有发现符合条件的主播时，不创建空文件。
- 首版沿用旧补丁对 Link/Battle 消息的字段识别规则，增加格式校验、资源限制和异常处理，不扩展完整连麦协议。
- 使用受控协议样例和自动化测试验证；实际直播仍须验证识别效果，测试不代表覆盖平台全部消息格式。

## 本轮交付边界

- 完成源码迁移、全局设置界面、相关测试和使用文档，提交到 `custom`。
- 小红书、镜像发布工作流、远程推送和部署切换不属于本轮实现范围。

## 验收场景

- 默认关闭；只读取抖音全局设置，不接受直播间配置覆盖。
- 开关变化不改变当前录制，下一次录制才生效。
- 关闭弹幕仍可记录名单；弹幕原有行为与 Cookie 模式保持正常。
- 过滤本人、普通上麦观众及无效身份，UID 不发生大整数精度丢失。
- 路径未就绪先缓存；分段和重复消息不会重复写入；新一次录制可以再次记录同一主播。
- 写入失败后仍保留首次发现时间；后续消息、分段和停止录制会触发重试。
- 停止录制时最后补写有等待上限，失败有日志和时间线提示，不因名单写入阻塞录像停止。
- 首次输出路径固定，无主播时不创建空文件。

## 已发现的旧实现问题

- 原补丁在录像路径尚未就绪时，先标记已记录再缓存；稍后补写会被去重判断跳过。新实现必须在成功写入后确认记录，并覆盖缓存补写场景。
- 原补丁按 Link/Battle 消息中的 Protobuf 字段启发式提取身份；迁移不能把所有消息中的用户都当作连麦主播，也不能承诺由此得到完整上下麦事件。

- 应用 Node 与 Web 两端类型检查通过。
